### [What are Static SQL Statements?]{#STATICSQL}

Static SQL Statements are SQL instructions that are a part of the
language syntax. Static SQL Statements can be used directly in the
source code as a normal procedural instruction. The static SQL
statements are parsed and validated at compile time. At runtime, these
SQL statements are automatically [prepared and
executed](DynamicSql.html) by the runtime system.

Program [variables](Variables.html) are detected by the compiler and
handled as SQL parameters.

The following example defines two variables that are directly used in an
`INSERT` statement:

``` linenumber
01 MAIN
02    DEFINE iref INTEGER, name CHAR(10)
03    DATABASE stock
04    LET iref = 65345
05    LET name = "Kartopia"
06    INSERT INTO item ( item_ref, item_name ) VALUES ( iref, name )
07    SELECT item_name INTO name
08      FROM item WHERE item_ref = iref
09 END MAIN
```

Using Static SQL Statements clarifies the source code (you do not need
to use [Dynamic SQL Instructions](DynamicSql.html) to prepare and
execute the SQL statement), but you cannot modify the SQL text at
runtime.

A limited number of SQL statements is directly supported in the language
(see below), but most common statements like `INSERT`, `UPDATE`,
`DELETE`, `SELECT` can be executed without problems using a simple
standard syntax.

### [Using program variables in Static SQL statements]{#VARIABLES}

The syntax of Static SQL statements supports the usage of program
variables directly as SQL parameters. This gives a better understanding
of the source code and requires less lines as using SQL parameters with
[Dynamic SQL](DynamicSql.html): 

``` linenumber
01 MAIN
02    DEFINE c_num INTEGER
03    DEFINE c_name CHAR(10)
04    DATABASE stock
05    SELECT cust_name INTO c_name FROM customer WHERE cust_num = c_num
06 END MAIN
```

If a database column name conflicts with a program variable, you can use
the @ sign as the column prefix. The compiler will treat the identifier
following the @ as a table column:

``` linenumber
01 MAIN
02    DEFINE cust_name CHAR(10)
03    DEFINE cnt INTEGER
04    DATABASE stock
05    SELECT COUNT(*) INTO cnt FROM customer WHERE @cust_name = cust_name
06 END MAIN
```

The @ sign will not figure in the resulting SQL statement stored in the
**42m** module.

### [Table and column names in Static SQL]{#TABCOLNAMES}

In Static SQL, table and column names will be converted to lowercase by
the [fglcomp](Tools.html#TL_FGLCOMP) compiler. The SQL keywords are
always converted to uppercase.

For example:

``` linenumber
01  UPDATE CUSTOMER set CUST_name = 'undef' WHERE cust_name is null
```

will be converted to:

    UPDATE customer SET cust_name = 'undef' WHERE cust_name IS NULL

While SQL keywords are not case sensitive for database servers, table
names and column names can be case-sensitive.

For more details, see [Naming database
objects](SqlProgramming.html#PORT_NAMOBJ).

### [What SQL string was generated by the compiler?]{#WHATSQL}

As described in the above sections, the [fglcomp](Tools.html#TL_FGLCOMP)
compiler parses the Static SQL statements and modifies them before
writing the resulting SQL text to the **42m** module.

You can extract all SQL statements from the source by using the -S
option of [fglcomp](Tools.html#TL_FGLCOMP):

``` linenumber
01 MAIN
02    DEFINE c_name CHAR(10)
03    DEFINE cnt INTEGER
04    DATABASE stock
05    SELECT COUNT(*) INTO cnt FROM customer WHERE customer.cust_name = c_name
06 END MAIN
```

    $ fglcomp -S test.4gl
    test.4gl^5^SELECT COUNT(*) FROM customer WHERE cust_name = ?

### [INSERT]{#SS_INSERT}

#### Purpose:

Inserts a row in a table in the [current database
session](Connections.html).

#### Syntax 1:

`INSERT INTO `*`table-specification`*` `[`[`]{.underline}` ( `*`column`*` `[`[,...]`]{.underline}` ) `[`]`]{.underline}\
[`{`]{.underline}\
`  VALUES ( `[`{`]{.underline}` `*`variable`*` `[`|`]{.underline}` `*`literal`*` `[`|`]{.underline}` NULL `[`}`]{.underline}` `[`[,...]`]{.underline}` )`\
[`|`]{.underline}\
`  `*`select-statement`*\
[`}`]{.underline}

#### Syntax 2: *Schema-dependent!*

`INSERT INTO `*`table-specification`*` VALUES ( `*`record`*`.* )`

#### Syntax 3: *Schema-dependent, removes serial columns!*

`INSERT INTO `*`table-specification`*` VALUES `*`record`*`.*`

where *table-specification* is:

`[`*`dbname`*`[@`*`dbserver`*`]:][`*`owner`*`.]`*`table`*

#### Notes:

1.  *dbname* identifies the database name. **Informix only!**
2.  *dbserver* identifies the Informix database server (INFORMIXSERVER).
    **Informix only!**
3.  *owner* identifies the owner of the table, with optional double
    quotes. **Informix only!**
4.  *table* is the name of the database table.
5.  *column* is a name of a table column.
6.  *variable* is a program [variable](Variables.html), a
    [record](Records.html) member or an [array](Arrays.html) member used
    as a parameter buffer to provide values.
7.  *literal* is any [literal expression](Literals.html) supported by
    the language.
8.  *select-statement* is a static [SELECT](#SS_SELECT) statement with
    or without parameters as variables.
9.  *record* is the name of a [record](Records.html) (followed by dot
    star in this syntax).

#### Usage:

The Static-SQL INSERT statement can be written in three different ways:

1.  **Syntax 1**: This is the most standard syntax, working with all
    type of database engines.
2.  **Syntax 2**: This syntax requires a database schema specification
    ([SCHEMA](DatabaseSchema.html)) and the corresponding **.sch**
    file.\
    The fglcomp compiler will automatically extend the SQL text with the
    columns identified by the record variable and generate a standard
    INSERT statement.
3.  **Syntax 3**: This last syntax is similar to syntax #2, except that
    it does not use braces around the record.\* specification.\
    Like syntax #2, it uses a `record.*` specification, which can be
    defined [LIKE](Variables.html#VA_DEFINE) a table described in the
    schema file. However, unlike syntax #2, if a record member was
    created from a column defined as SERIAL, SERIAL8 or BIGSERIAL in the
    [schema file](DatabaseSchema.html), that record member will be
    removed from the value list. 

When using the `VALUES` clause, the statement inserts a row in the table
with the values specified in variables, as literals, or with `NULL`. If
a [record](Records.html) is available, you can specify all record
members with the star notation (`record.*`).

When you use a *select-statement*, the statement insert all rows
returned in the result set of the [SELECT](#SS_SELECT) statement.

The syntax #3 can be used to avoid serial column usage in the value
list: The record member corresponding to a column defined as SERIAL,
SERIAL8 or BIGSERIAL in the schema file will be removed by the compiler.
This is useful when using databases like SQL Server, where IDENTITY
columns must be omitted in INSERT statements.

#### Warnings:

1.  For portability, it is not recommended that you use the
    *select-statement* syntax.
2.  When you use a *select-statement*, the columns returned by the
    result set must match the column number and data types of the target
    table.

#### Example:

``` linenumber
01 MAIN
02    DEFINE myrec RECORD
03             key INTEGER,
04             name CHAR(10),
05             cdate DATE,
06             comment VARCHAR(50)
07          END RECORD
08    DATABASE stock
09    LET myrec.key     = 123
10    LET myrec.name    = "Katos"
11    LET myrec.cdate   = TODAY
12    LET myrec.comment = "xxxxxx"
13    INSERT INTO items VALUES ( 123, 'Practal', NULL, myrec.comment )
14    INSERT INTO items VALUES ( myrec.* )
15    INSERT INTO items VALUES myrec.*  -- without serial (if one is used)
16    INSERT INTO items SELECT * FROM histitems WHERE name = myrec.name
17 END MAIN
```

### [UPDATE]{#SS_UPDATE}

#### Purpose:

Updates rows of a table in the [current database
session](Connections.html).

#### Syntax 1:

`UPDATE `*`table-specification`\*
`   SET`\
`       `*`column`*` = `[`{`]{.underline}` `*`variable`*` `[`|`]{.underline}` `*`literal`*` `[`|`]{.underline}` NULL `[`}`]{.underline}\
`       `[`[,...]`]{.underline}\
`   `[`[`]{.underline}` `*`sql-condition`*` `[`]`]{.underline}

#### Syntax 2:

`UPDATE `*`table-specification`*\
`   SET ( `*`column`*` `[`[,...]`]{.underline}` )`\
`     = ( `[`{`]{.underline}` `*`variable`*` `[`|`]{.underline}` `*`literal`*` `[`|`]{.underline}` NULL `[`}`]{.underline}` `[`[,...]`]{.underline}` )`\
`   `[`[`]{.underline}` `*`sql-condition`*` `[`]`]{.underline}

#### Syntax 3: Informix only!

`UPDATE `*`table-specification`*\
`   SET `[`[`]{.underline}*`table`*`.`[`]`]{.underline}`*`\
`     = ( `[`{`]{.underline}` `*`variable`*` `[`|`]{.underline}` `*`literal`*` `[`|`]{.underline}` NULL `[`}`]{.underline}` `[`[,...]`]{.underline}` )`\
`   `[`[`]{.underline}` `*`sql-condition`*` `[`]`]{.underline}

#### Syntax 4: *Schema-dependent!*

`UPDATE `*`table-specification`*\
`   SET `[`{`]{.underline}` `[`[`]{.underline}*`table`*`.`[`]`]{.underline}`* `[`|`]{.underline}` ( `*`column`*` `[`[,...]`]{.underline}` ) `[`}`]{.underline}\
`     = `*`record`*`.*`\
`   `[`[`]{.underline}` `*`sql-condition`*` `[`]`]{.underline}

where *table-specification* is:

`[`*`dbname`*`[@`*`dbserver`*`]:][`*`owner`*`.]`*`table`*

and *sql-condition* is:

`WHERE `[`{`]{.underline}` `*`condition`*` `[`|`]{.underline}` CURRENT OF `*`cursor`*` `[`}`]{.underline}` `

#### Notes:

1.  *dbname* identifies the database name. **Informix only!**
2.  *dbserver* identifies the Informix database server (INFORMIXSERVER).
    **Informix only!**
3.  *owner* identifies the owner of the table, with optional double
    quotes. **Informix only!**
4.  *table* is the name of the database table.
5.  *column* is a name of a table column.
6.  *column* can be specified with a sub-script expression
    (`column[a,b]`). **Informix only!**
7.  *variable* is a program [variable](Variables.html), a
    [record](Records.html) member or an [array](Arrays.html) member used
    as a parameter buffer to provide values.
8.  *literal* is any [literal expression](Literals.html) supported by
    the language.
9.  *record* is the name of a [record](Records.html) (followed by dot
    star in this syntax).
10. *condition* is an SQL expression to select the rows to be updated.
11. *cursor* is the identifier of a [database cursor](ResultSets.html).
12. For more details about the `WHERE CURRENT OF` clause, see
    [Positioned Updates](PositionedUpdates.html).

#### Usage:

The Static-SQL UPDATE statement can be written in three different ways:

1.  **Syntax 1**: This is the most standard syntax, working with all
    type of database engines.
2.  **Syntax 2**: This syntax comes from Informix 4GL, but can also be
    used with other RDBMS, because the compiler converts the SQL
    statement to a portable syntax, using standard column assignments (
    UPDATE table SET col1 = ?, col2, ?, \... ).
3.  **Syntax 3**: This syntax is Informix specific, and is not converted
    by the compiler, so it should be avoided.
4.  **Syntax 4**: The last syntax requires a database schema
    specification ([SCHEMA](DatabaseSchema.html)) and the corresponding
    **.sch** file.\
    The fglcomp compiler will automatically extend the SQL text with the
    columns identified by the record variable.\
    The columns defined in the **.sch** file as SERIAL (code 262) will
    be omitted in the generated column list.

#### Warnings:

1.  The third syntax (**Syntax 3**) should be avoided, since it is
    Informix specific. 
2.  The fourth syntax (**Syntax 4**) can be used if the [database schema
    file](DatabaseSchema.html) has been generated with the correct
    Informix-equivalent data types. This is especially important when
    using SERIAL columns or equivalent auto-incremented columns.
3.  *column* with a sub-script expression (`column[a,b]`) is not
    recommended because most database servers do not support this
    notation.

#### Example:

``` linenumber
01 MAIN
02    DEFINE myrec RECORD
03             key INTEGER,
04             name CHAR(10),
05             cdate DATE,
06             comment VARCHAR(50)
07          END RECORD
08    DATABASE stock
09    LET myrec.key     = 123
10    LET myrec.name    = "Katos"
11    LET myrec.cdate   = TODAY
12    LET myrec.comment = "xxxxxx"
13    UPDATE items SET
14         name    = myrec.name,
15         cdate   = myrec.cdate,
16         comment = myrec.comment
17     WHERE key = myrec.key
18 END MAIN
```

### [DELETE]{#SS_DELETE}

#### Purpose:

Deletes rows from a table in the [current database
session](Connections.html).

#### Syntax:

`DELETE FROM `*`table-specification`\*
`   `[`[`]{.underline}` WHERE `[`{`]{.underline}` `*`condition`*` `[`|`]{.underline}` CURRENT OF `*`cursor`*` `[`}`]{.underline}` `[`]`]{.underline}

where *table-specification* is:

`[`*`dbname`*`[@`*`dbserver`*`]:][`*`owner`*`.]`*`table`*

#### Notes:

1.  *dbname* identifies the database name. **Informix only!**
2.  *dbserver* identifies the Informix database server (INFORMIXSERVER).
    **Informix only!**
3.  *owner* identifies the owner of the table, with optional double
    quotes. **Informix only!**
4.  *table* is the name of the database table.
5.  *condition* is an SQL expression to select the rows to be deleted.
6.  *cursor* is the identifier of a [database cursor](ResultSets.html).
7.  For more details about the `WHERE CURRENT OF` clause, see
    [Positioned Updates](PositionedUpdates.html).

#### Warnings:

1.  If you do not specify the `WHERE` clause, all rows in the table will
    be deleted.

#### Example:

``` linenumber
01 MAIN
02    DATABASE stock
03    DELETE FROM items WHERE name LIKE 'A%'
04 END MAIN
```

### [SELECT]{#SS_SELECT}

#### Purpose:

Selects rows from one or more tables in the [current database
session](Connections.html).

#### Syntax:

*`select-statement`*` `[`[`]{.underline}` UNION `[`[`]{.underline}`ALL`[`]`]{.underline}` `*`select-statement`*` `[`]`]{.underline}` `[`[...]`]{.underline}

where *select-statement* is:

`SELECT `[`[{`]{.underline}`ALL`[`|`]{.underline}`DISTINCT`[`|`]{.underline}`UNIQUE`[`}]`]{.underline}` `[`{`]{.underline}` * `[`|`]{.underline}` `*`select-list`*` `[`}`]{.underline}\
`  `[`[`]{.underline}` INTO `*`variable`*` `[`[,...]`]{.underline}` `[`]`]{.underline}\
`  FROM `*`table-list`*` `[`[,...]`]{.underline}\
`  `[`[`]{.underline}` WHERE `*`condition`*` `[`]`]{.underline}\
`  `[`[`]{.underline}` GROUP BY `*`column-list`*` `[`[`]{.underline}` HAVING `*`condition`*` `[`]`]{.underline}` `[`]`]{.underline}\
`  `[`[`]{.underline}` ORDER BY `*`column`*` `[`[{`]{.underline}`ASC|DESC`[`}]`]{.underline}` `[`[,...]`]{.underline}` `[`]`]{.underline}` `

where *select-list* is:

[`{`]{.underline}` `[`[`]{.underline}`@`[`]`]{.underline}*`table-specification`*`.*`\
[`|`]{.underline}` `[`[`]{.underline}*`table-specification`*`.`[`]`]{.underline}*`column`\*
[`|`]{.underline}` `*`literal`\*
[`}`]{.underline}` `[`[`]{.underline}` `[`[`]{.underline}`AS`[`]`]{.underline}` `*`column-alias`*` `[`]`\
`[,...]`]{.underline}

where *table-list* is:

[`{`]{.underline}` `*`table-name`*[\
`|`]{.underline}` OUTER `*`table-name`*[\
`|`]{.underline}` OUTER ( `*`table-name`*` `[`[,...]`]{.underline}` )`[\
`}`\
`[,...]`]{.underline}

where *table-name* is:

*`table-specification`*` `[`[`]{.underline}` `[`[`]{.underline}`AS`[`]`]{.underline}` `*`table-alias`*` `[`]`]{.underline}

where *table-specification* is:

`[`*`dbname`*`[@`*`dbserver`*`]:][`*`owner`*`.]`*`table`*

where *column-list* is:

*`column-name`*` `[`[,...]`]{.underline}` `

where *column-name* is:

[`[`]{.underline}*`table`*`.`[`]`]{.underline}*`column`*

#### Notes:

1.  *dbname* identifies the database name. **Informix only!**
2.  *dbserver* identifies the Informix database server (INFORMIXSERVER).
    **Informix only!**
3.  *owner* identifies the owner of the table, with optional double
    quotes. **Informix only!**
4.  *table* is the name of the database table.
5.  *table-alias* defines a new name to reference the *table* in the
    rest of the statement.
6.  *column* is a name of a table column.
7.  *column-alias* defines a new name to reference the *column* in the
    rest of the statement.
8.  *condition* is an SQL expression to select the rows to be deleted.
9.  The `INTO` clause provides the list of fetch buffers. This clause is
    not part of the SQL language sent to the database server; it is
    extracted from the statement by the compiler.

#### Warnings:

1.  The language supports the `SELECT INTO TEMP` statement to create
    temporary tables (this statement does not return a result set).

#### Usage:

If the `SELECT` statement returns [only one row]{.underline} of data,
you can write it directly as a procedural instruction. However, you must
use the `INTO` clause to provide the list of [variables](Variables.html)
where column values will be fetched:

``` linenumber
01 MAIN
02    DEFINE myrec RECORD
03             key INTEGER,
04             name CHAR(10),
05             cdate DATE,
06             comment VARCHAR(50)
07          END RECORD
08    DATABASE stock
09    LET myrec.key = 123
10    SELECT name, cdate
11      INTO myrec.name, myrec.cdate
12      FROM items
13      WHERE key=myrec.key
14 END MAIN
```

If the `SELECT` statement returns [more than one row]{.underline} of
data, you must declare a database cursor to process the result set:

``` linenumber
01 MAIN
02    DEFINE myrec RECORD
03             key INTEGER,
04             name CHAR(10),
05             cdate DATE,
06             comment VARCHAR(50)
07          END RECORD
08    DATABASE stock
09    LET myrec.key = 123
10    DECLARE c1 CURSOR FOR
11      SELECT name, cdate
12        FROM items
13        WHERE key=myrec.key
14    OPEN c1
15    FETCH c1 INTO myrec.name, myrec.cdate
16    CLOSE c1
17 END MAIN
```

The `SELECT` statement can include the `INTO` clause, but it is strongly
recommended that you use that clause in the
[FETCH](ResultSets.html#RS_FETCH) instruction only.

See [Result Sets Processing](ResultSets.html) for more details.
